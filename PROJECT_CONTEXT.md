# Second-Brain for a Researcher

### Agentic research pipeline for literature + code discovery, built on Claude Code + Claude app + Obsidian

## Motivation

Methods relevant to a problem often already exist in an adjacent field, but finding them is manual and ad hoc — and whatever we do find rarely gets captured anywhere durable, so the next project starts from zero. Example: MedDINOv3 embeddings underperformed on sarcopenia CT without finetuning, for reasons (CLS-token pooling losing texture signal, domain gap from natural-image pretraining) that were already documented in the literature — we just weren’t systematically searching for it.

## Core pipeline (7 stages)

1. **Intake** — researcher provides domain, data description, reference standard, task, via Claude app or Claude Code. Metadata/description level only — no patient data ever enters the system. Alternatively, a **topic review**: no problem or dataset, just a topic plus scope, purpose and 1–5 guiding questions (`profile_type: topic`). Relevance downstream is then anchored on those questions instead of a failure mode; search depth is unchanged, but the date window is set per profile (`date_window_years`).
2. **Problem profile** — interactive Q&A deepens the profile, written to a new Obsidian project note.
3. **Discovery (parallel)**
   - Papers: arXiv API, PubMed E-utilities, Semantic Scholar Graph API. Two passes — close-field terms, then generalized methodology terms (for cross-field transfer hits).
   - Code: GitHub, matched to discovered papers where possible.
4. **Checkpoint** — pipeline pauses here for researcher review/approval before anything is cloned or executed.
5. **Vault build**
   - Papers: structured fields (problem, data/modality, method, result, code link) + a short synthesis (why relevant, what would need to change to apply it, one skeptical note) extracted from ar5iv/PMC full text where available, PDF fallback otherwise.
   - Repos: cloned, structure/classes summarized into a note; optionally run/tested in a local Docker sandbox.
6. **Cross-linking** — paper and repo notes linked to each other and to the problem node (embedding similarity for “related” links), forming a browsable Obsidian graph.
7. **Experiment plan** — proposes baseline + ideas; can adapt code from the repo vault directly into the researcher’s *existing* project repo (not a new one).

## Architecture

- **Claude app** — intake, Q&A, review/approval at checkpoints.
- **Claude Code** — orchestrates search, cloning, analysis, sandboxed execution.
- **External sources** — arXiv, PubMed, Semantic Scholar, GitHub APIs.
- **Local Docker sandbox** — runs/tests cloned code, isolated from production data.
- **Obsidian vault** — personal, local, per researcher. Cross-project linking is an optional per-project toggle (e.g. a segmentation paper relevant to both EPAT and sarcopenia work).

## Constraints / decisions locked in

- No patient data ever referenced — profile stays at modality/cohort/task description level.
- ~~Paywalled papers are flagged for manual download, not auto-fetched.~~ **Superseded by operator decision.** The fetch chain now tries open access first and falls back to Sci-Hub for what OA cannot resolve; only a paper that resolves *nowhere* is flagged for manual download, and the stage-4 checkpoint stops on that list. Sci-Hub distributes paywalled papers without publisher authorization and is legally contested in most jurisdictions — this is a deliberate choice by the pipeline's operator, and it is worth re-weighing given that this repo is public and self-hosts a marketplace, so the behavior ships to anyone who installs the plugin rather than staying local.
- Pipeline pauses after discovery, before any cloning or code execution.
- Experiment-plan code reuse targets the existing project repo, not a fresh one.
- Built and maintained by [you] + one collaborator.
- MVP = full pipeline in reduced form (fewer sources, simpler linking); no committed timeline yet, direction only.
- Every agent's `description:` must warn against being reimplemented from the description alone or routed around after a blocking completion report — it's the only content ambiently visible to an orchestrating session before dispatch (no plugin-level CLAUDE.md equivalent exists), and a past incident showed exactly that: a session treated a subagent's correct "needs a restart" report as license to fabricate the job itself.
- `arxiv-mcp-server` is declared as a real cross-marketplace dependency in `plugin.json`/`marketplace.json`. Verified by live testing (not assumed): the `dependencies` field auto-installs and auto-enables it — including a previously-`failed to load` install self-healing to enabled with no restart — but only once `arxiv-mcp-server`'s own marketplace is already registered; it does not auto-add an unregistered marketplace. README's install section adds both marketplaces up front for exactly this reason.
- **Agent vs. skill split.** A piece is a *skill* only if it needs the main conversation: `research-problem-intake` runs a live adaptive Q&A, `second-brain-pipeline` has to hold the stage-4 checkpoint across a real turn, and `second-brain-topic-deep-dive` may have to ask which vault or note is meant before handing over to both (a dispatched agent runs to completion and returns once, so it structurally cannot pause for approval). Everything else is an *agent* — bounded, non-conversational work with a system-enforced `tools:` allowlist. `obsidian-vault` was originally a skill whose whole body was "dispatch a subagent," with that subagent existing only as prose; it became `agents/obsidian-vault-writer.md`, so its tool scope was actually enforced rather than merely instructed — and has since been replaced by `scripts/build_vault.py`, since the job turned out to need no model at all. - **Workers never ask, never check the environment, never resolve their own inputs.** The orchestrator owns all three. An agent runs once and returns, so it structurally cannot pause for a human answer — any instruction telling one to "ask" is a bug (both `obsidian-vault-writer` and `paper-summarizer` had one). Every input an agent needs is passed explicitly by `second-brain-pipeline`, which is why template-path resolution lives in the pipeline and not in `paper-summarizer`. Agents report problems; the pipeline decides what to do about them and re-dispatches.
- **Model tiers are pinned per agent, never `inherit`.** Per-item and mechanical work runs on `sonnet`: the discovery legs (fit screening happens there), `paper-summarizer` (one dispatch per paper, each reading a 20–140 KB full text). Vault-build was a third `sonnet` agent, `obsidian-vault-writer`, until it became a script (see below). Only `topic-summarizer`, the cross-paper synthesis and core-equation extraction, is pinned to `opus`. `inherit` is avoided because it ties quality to whatever model the orchestrating session runs on: pinning lets the researcher run the main session on Sonnet without downgrading synthesis, and stops a main session on Opus from silently running 30+ summarizer dispatches on Opus. The orchestrator itself reads only file headers during the stage-3 merge and greps `keywords` for the stage-5 index, for the same reason.
- **Topic notes partially realize spec stage 6, but not the way the spec describes it.** `topic-summarizer` writes one note per subtopic, built from the papers sharing that `keywords` slug, which does link papers to each other through a shared node. That is **keyword-based**, not the **embedding-similarity** linking stage 6 actually specifies — the embedding-model choice is still an open question below. Don't let a populated `topics/` folder be read as evidence that similarity linking is done.

  **Updated (2026-09-24):** paper-to-paper links are computed by a **script**, `scripts/link_papers.py` (stdlib Python, run by the pipeline with Bash), not by an agent. The `similarity-linker` agent was removed after an eval. Setup: a 12- and a 41-paper vault, Haiku vs Sonnet, 2 runs each, scored against ground truth computed from Semantic Scholar. Results:
  - Both models had 100% precision but found almost no bibliographic couplings, which make up most of the graph (355 candidates vs 37 direct citations on the 41-paper vault).
  - Haiku found 0–4% of the couplings, wrote one-way edges whenever the cap applied, and reported that no pairs qualified.
  - Sonnet found 14–61% on 12 papers and 0–8% on 41, at $3–4 per run, and twice tried to write a script itself.

  The script scores 100% on all of it, with zero structural errors, for no model cost.

  It gets everything from one Semantic Scholar `POST /graph/v1/paper/batch` call (≤500 ids; `arXiv:`, `DOI:` and `PMID:` all accepted). That call returns reference lists and SPECTER2 embeddings, so PubMed papers get the same citation linking as arXiv papers, with no Asta dependency and no citations-only asymmetry. The 41-paper fetch took 3 s, against ~25 min for per-paper calls under the shared quota.

  Link kinds:
  - **Direct citation.**
  - **Shared references:** ≥2 references outside the vault. One shared reference is usually a benchmark or dataset paper, and would link everything to everything.
  - **Similar content:** SPECTER2 cosine ≥0.90, only for pairs with no citation relation.

  Slots are capped per paper: 5 citation, 3 content. Edges are chosen greedily in one global order, so every edge is symmetric and deterministic by construction. The reason for each link goes into `related_basis`.

  The script records the entries it wrote in `<paper_vault>/.linker/owned.json`. On a re-run it replaces only its own entries, so hand-added links survive and edges to a regenerated summary's old id are dropped rather than left dead.

  Vault-build (now `scripts/build_vault.py`) renders `## Related` grouped by basis, because Obsidian builds no graph edge from a bare list of ids in frontmatter: unrendered, the edges would exist in the file and not in the graph. Content links are labelled as estimates.

  **Stage 6 is now implemented in reduced form**, with two limits:
  - Content similarity uses Semantic Scholar's precomputed SPECTER2 embeddings, which cover **title and abstract only**, not full text.
  - It covers only papers S2 has an embedding for. The script names the rest (`no_content_links_possible`, `not_in_s2`) and reports coverage, so a missing link never reads as "unrelated".

  No local model and no index are needed. A local SPECTER2 run for the papers S2 lacks is a possible opt-in, deferred because of the torch dependency. Mixing in a different model's scores is ruled out: SPECTER2 cosines are compressed (0.76–0.97 on the calibration vault), so another model's numbers would make the floor meaningless.

  The 0.90 floor was calibrated on one 41-paper vault: same-field neighbours scored 0.92–0.97, and the closest cross-field pair (CT imaging vs time-series) 0.861. Re-check it on a vault that genuinely spans fields. Cross-field methods matches are the case this project wants most, and they may sit just under the floor.

  Rejected alternatives: `arxiv-mcp-server`'s `semantic_search` needs the `[pro]` extra and covers only arXiv papers in the local cache, so it would silently miss the entire PubMed leg. Note also that Asta exposes **no recommendations tool** — the Phase 3 plan had assumed Semantic Scholar's Recommendations API was reachable through it, and it is not; Asta's eight tools are lookup, search, snippet and citations only. Scope for this version is per-problem (`<vault>/<problem-id>/topics/`); vault-global topic notes accumulating across problems would need merge-on-rerun logic and are a later pass.
- **Code discovery is API-only, and that is what lets it run before the checkpoint.** Spec stage 3b is now built as `second-brain-code-finder`, but it never clones, downloads, or executes anything: `gh api .../readme` plus `gh api .../git/trees/<branch>?recursive=1` supply everything a repo note needs (verified — 56 files returned for a real repo with nothing written to disk). That matters structurally rather than cosmetically. The locked-in constraint above is that the pipeline pauses before anything is cloned or executed, and this leg runs *before* that pause; an API-only agent can therefore be part of discovery, where a cloning one could not. `code_vault_path` stays empty and the checkpoint says so explicitly, so its emptiness reads as intended rather than as a failed step.

  **It runs after the three paper legs, not in parallel with them** — its highest-precision source is the repos named inside the saved papers (measured: 41 distinct GitHub/GitLab URLs across 35 cached papers, ~1.2 per paper), so started in parallel it would find an empty vault and quietly degrade to topic search, the weaker half of what it does. `summaries/` does not exist yet at that point either, so `code_link` is a re-run-only source and the full-text grep is the primary one.

  **Screening is where the value is, and two fields do most of it.** `license.key` empty means *no license* — recorded as `none`, flagged, ranked down, never silently dropped, because unlicensed code grants no reuse rights however good it is and that is invisible at a glance. And `provenance` (official-implementation / reimplementation / dependency-or-dataset / search-hit) usually beats star count: a 40-star repo linked from the paper you care about produced the results you read; a 3k-star reimplementation did not.

  **Prior art rejected, with a live upgrade path.** [Repomix](https://github.com/yamadashy/repomix) (MIT, ~26k★) is the category leader for repo→LLM digests — `pack_remote_repository`, Tree-sitter `--compress`, its own MCP server — but it is npm-only and `node`/`npm`/`npx` are absent on this machine, and `gh api` already covers an API-only note. [gitingest](https://github.com/cyclotruc/gitingest) is the Python equivalent and does run here via `uvx` (verified); it is the right addition if source-level digests are ever wanted, since it needs no new package manager. Neither is needed to make repos legible, which is all this phase claims to do.

- **Merge-on-rerun is plain file I/O; the Obsidian REST API turned out not to be needed for it.** The plan adopted `obsidian-local-rest-api` specifically because its `PATCH /vault/{path}` can edit one heading without touching the rest of a file — the deferred "preserve manual edits" requirement. Working through it, that requirement does not actually need the API: vault-build (then `obsidian-vault-writer`, now `scripts/build_vault.py`) already reads and writes these files, so it can split a note into frontmatter plus `##` sections, regenerate only the sections it owns (`## Links`, `## Citation`, `## Related`, and the `## Papers`/`## Topics` link lists), and preserve everything else verbatim. Same outcome, no API key, no plugin, no running application.

  What the REST path would have added is worse than nothing here. It writes vault-relative paths into **whichever vault Obsidian currently has open**, which is not necessarily the `obsidian_vault/<problem-id>/` the pipeline computed — so a mismatch would silently write a problem's notes into an unrelated vault, and the failure would look like missing output rather than misplaced output. It also needs a bearer token, an enabled community plugin, a running Obsidian, and (on the default HTTPS port 27124) a self-signed certificate. Verified on this machine: Obsidian 1.13.7 is installed via Flatpak but nothing is listening on 27123/27124, so the path could not have been tested even if built.

  Reconsider only if a workflow appears that genuinely needs Obsidian's own indexer — alias and wikilink resolution the way Obsidian resolves them — which file-level Markdown access cannot reproduce. That was the original bar in `OBSIDIAN_VAULT_OPEN_QUESTIONS.md` and it is still the right one.
- **Vault-build does not depend on Obsidian being installed.** A vault is a folder of markdown files. `obsidian-vault-writer` originally returned `approval_required` and refused to write anything when the app was missing — backwards, since the notes could have been written regardless. The install check belonged only to *opening* the result, which is now an optional convenience step after stage 5 in `second-brain-pipeline`. Auto-install was dropped entirely (it was `winget`-only, so Windows-only, and wouldn't work under WSL anyway): the pipeline offers to launch Obsidian if present, and otherwise just reports the vault path. Installing software on the researcher's machine is out of scope.
- **One copy of each schema.** `templates/research-problem-profile-format-spec.md` and `templates/paper-page-template.md` are the only definitions of those two contracts. `skills/obsidian-vault/references/{problem-profile,paper-note}.md` used to restate both independently — deleted, because the vault stage's *input* is the summarizer stage's *output*, so any drift between the two copies would break the handoff silently. New consumers cite the `templates/` files; don't restate a schema locally.
- Also verified live (both the real install path and `claude --plugin-dir`): when `arxiv-mcp-server` is missing, Claude Code's plugin loader refuses to load `second-brain-researcher` at all — every agent and skill in it is completely unreachable, not just degraded. Because of this, `second-brain-paper-downloader` no longer contains its own `claude plugin list` dependency check (removed — it was a leftover from before the `dependencies` field existed, and could never actually run: the loader already blocks the whole plugin upstream in every supported invocation path). The general "don't improvise a substitute for a subagent that can't proceed" guardrail in the agent descriptions (see above) is unrelated to this and stays — it covers any reason an agent can't proceed, not specifically this dependency.

- **arXiv MCP tool names must be allowlisted under both prefixes.** The agents originally named only `mcp__plugin_arxiv-mcp-server_arxiv__*`, which is correct *only* when `arxiv-mcp-server` is installed as a Claude Code plugin. Configured instead as an ordinary user-level stdio server named `arxiv` (`uvx arxiv-mcp-server` in `~/.claude.json`) — which is how it is set up on at least one dev machine, where `~/.claude/plugins/` does not exist at all — the live tools are `mcp__arxiv__*` and the agent silently has **no arXiv tools whatsoever**. Both forms are now allowlisted in every agent that touches arXiv, and the bodies refer to the tools by bare name (`search_papers`, `get_abstract`, …) with the prefix explained once. This is a real failure mode, not a hypothetical: an allowlist naming a tool that doesn't exist produces no error, just an agent that can't work.
- **Use the dependency you already have before adding another.** `arxiv-mcp-server` exposes 19 tools; the plugin called 3. Two capabilities that were being hand-rolled in prose are now delegated: `topic-summarizer`'s grep-then-`Read`-with-offset dance over 20–140 KB full texts is `search_paper_text` + `read_paper_section` + `get_paper_outline` (the Grep path is kept as the documented fallback for non-arXiv papers and for ids the server doesn't hold), and vault-build now attaches BibTeX from arXiv's own metadata rather than leaving bibliography as an open question. It began as one batched `export_citations` call; since vault-build became a script, `scripts/build_vault.py` requests the same arXiv API directly and formats entries exactly as `export_citations` does (verified byte-identical on the reRD vault), falling back to OAI-PMH per id when the query API refuses — it answered HTTP 406 to every uncached request on 2026-09-24. No entry is ever written or repaired from any other field: the value is that the fields come from arXiv's metadata, so an invented citation is worse than an absent one. Still unused and worth revisiting: `citation_graph` (ranking), `semantic_search` (a stage-6 stopgap needing no new dependency).
- **`search_paper_text` matches literal substrings, and a miss is silent.** Verified against a cached paper: `point adjustment` returns passages, while `how does point adjustment overestimate detection performance` returns `status: success` with **zero** passages — a natural-language query is not an error, it is an empty result. Left unguarded this is the worst possible failure for `topic-summarizer`, because an empty search reads as "this paper doesn't discuss the subtopic" and gets written into a topic note as a literature gap that isn't real. `topic-summarizer` therefore instructs one call per short verbatim phrase, and to treat a zero-hit term as evidence about the wording rather than about the paper. Same family of gotcha as the `abs:` over-restriction caveat in `second-brain-paper-downloader`: the tool succeeds, the result is empty, and only the prose stops that becoming a false finding.
- **`paper-search-mcp` is bundled as an MCP server, not declared as a dependency.** The `dependencies` field in `plugin.json` accepts **marketplace plugins only** — and `openags/paper-search-mcp` has no `.claude-plugin/` directory, so it is not one; it ships a Claude Code *Skill*, a Smithery config, and a PyPI package. Declaring it as a dependency would have made the whole plugin fail to load, which is the documented all-or-nothing failure mode in `README.md`. It is instead bundled in a plugin-root `.mcp.json` as a server named `paper-search`, running `uvx paper-search-mcp` so there is nothing to install given `uv` on PATH. **Tool-prefix consequence:** a bundled server's tools are named `mcp__plugin_<plugin-name>_<server-name>__<tool>`, i.e. `mcp__plugin_second-brain-researcher_paper-search__*`, or `mcp__paper-search__*` if the researcher configures it themselves — both allowlisted, per the Phase 0 lesson. That naming rule is also the retroactive explanation of the arXiv bug above: `mcp__plugin_arxiv-mcp-server_arxiv__*` is plugin `arxiv-mcp-server`, server `arxiv`.
- **`download_with_fallback`'s `use_scihub` default was reviewed, then deliberately kept on.** It defaults to `True`, which initially looked like a dangerous default to guard — the biomedical fetcher would auto-pull paywalled papers once OA attempts failed, contradicting the then-standing flag-and-stop rule. Raised with the operator, who decided Sci-Hub fallback is wanted; the constraint above was superseded rather than the default overridden. What survives from that review is the ordering and the accounting: OA rungs run first and are preferred (faster, more reliable, better extractions), Sci-Hub is only for what OA could not resolve, a dead mirror counts as *unresolved* rather than *absent*, and anything resolving nowhere lands on an explicit needs-manual-download list that the stage-4 checkpoint refuses to skip past. **Updated (2026-09-24):** the biomedical leg no longer calls `download_with_fallback`; open access goes through `scripts/fetch_fulltext.py`, and the Sci-Hub rung is a direct `download_scihub` call for what that could not resolve — same operator decision, same order.
- **Do not default to MeSH tags on PubMed — measured, and the opposite of the intuition.** PubMed's Automatic Term Mapping already expands a bare term into its MeSH descriptor OR-ed with free-text fields, so `sarcopenia AND computed tomography` becomes `("sarcopenia"[MeSH Terms] OR "sarcopenia"[All Fields] …) AND ("tomography, x ray computed"[MeSH Terms] OR …)`. Tagging `[MeSH]` explicitly therefore **narrows**: 1378 hits vs. 3567 untagged, and 532 vs. 1296 restricted to the last two years. Because indexing lags publication, mandatory MeSH systematically drops the newest work. MeSH is a precision tool for narrowing a flooded query, never a recall fix.
- **PubMed's date window lives inside the query string.** `search_pubmed(query, max_results, sort)` has no date parameter, and `search_papers`'s `year` argument is Semantic Scholar-only — it is silently ignored for PubMed. But `PubMedSearcher.search` passes `'term': query` verbatim to ESearch, so the full PubMed query language is reachable: appending `AND ("2023"[Date - Publication] : "2026"[Date - Publication])` works. Verified through both the CLI and the MCP tool call — with the clause, years come back `[2024×6, 2025×2]`; without it, `[2018…2023]`. No E-utilities fallback is needed. One parsing note: the MCP response returns **concatenated JSON objects** in `content[0].text`, not a JSON array.
- **Asta's API key is effectively required, despite the docs saying otherwise — and failing without one is slow and misdiagnosable.** Ai2's page frames the key as "enables higher rate limits", implying keyless access merely throttles. Tested directly against `https://asta-tools.allen.ai/mcp/v1` with no key: `initialize` and `tools/list` succeed (8 tools), and identifier-lookup tools work — `search_paper_by_title` returned a correct result in 32s. But **both search tools fail**: `snippet_search` and `search_papers_by_relevance` each hang for roughly **271 seconds** and then return `Error executing tool …: RetryError[ConnectionRefusedError]`. Reproduced twice per tool. So the split is lookup-by-identifier keyless, discovery gated — and `snippet_search` is the single tool Asta was adopted for.

  **Since confirmed with a real key**: `snippet_search` returns in ~31s with relevant results, against the ~271s hang unauthenticated. The tool is worth the dependency; the gating is the only problem.

  Two consequences for `second-brain-crossfield-searcher`, now built into it. First, the key is a hard prerequisite, not an optimization; request it at `https://share.hsforms.com/1L4hUh20oT3mu8iXJQMV77w3ioxm`. Second, the failure mode is worse than a plain 401 — it is a four-and-a-half-minute hang ending in a *connection* error, which reads as a transient network fault rather than a missing credential. The agent must verify the key is configured **before** issuing search calls and fail fast with the real reason, rather than letting an unauthenticated run burn minutes per query and then report the wrong cause. Same family as the other three gotchas above: the call does not cleanly fail, and only the prose prevents a wrong diagnosis.

  Also note an asymmetry in the tool surface: `search_papers_by_relevance` and `get_citations` take a `publication_date_range`, but `snippet_search` does not — it only has `inserted_before`. The cross-field pass therefore cannot date-window its primary tool the way the arXiv and PubMed legs do.

- **Non-arXiv full text is Docling's job, and two flags decide whether it is usable.** `download_with_fallback` returns a PDF path, not text, so the biomedical leg converts before saving. Measured on a real Europe PMC paper: the default `--to md` embeds every figure as a base64 data URI, producing **545 KB** with a single **200,132-character** line, versus **56 KB** with `--image-export-mode placeholder` — same 24-heading structure either way. 56 KB sits inside the 20–140 KB band the arXiv extractions occupy, so the summarizer sees one consistent input shape. `--no-ocr` cuts 49s to 10s on born-digital journal PDFs. The existing >10 KB sanity check does double duty here: an under-10 KB result means the PDF was scanned and `--no-ocr` produced an empty shell, so that one paper is retried *with* OCR rather than OCR being paid for on every paper. Docling missing on `PATH` degrades the note to abstract-only; it never loses the paper. **Updated (2026-09-24):** Docling now runs inside `scripts/fetch_fulltext.py` with the same flags, and only for PDFs; the XML routes come first — see the full-text entry below.
- **`paywalled:` describes the paper; `pdf_local_path:` describes the fetch.** Keeping these separate matters once the fetch chain has several rungs that fail for unrelated reasons. `paywalled: true` means the open-access rungs could not resolve it — *including* when Sci-Hub then succeeded, because the paper is still behind a publisher paywall. `pdf_local_path` is blank whenever there is no local full text, whatever the cause. The trap, and the first draft of the biomedical agent fell into it, is marking a paper `paywalled: true` because *we* failed to capture text: a fully open-access paper that merely hit a missing Docling install is `paywalled: false` with a blank path, and recording it otherwise sends the researcher hunting for a subscription they already have. **Updated (2026-09-24):** in the saved paper file, `full_text: full | abstract-only` now plays the role `pdf_local_path` played here; the distinction is unchanged.

- **`read_pubmed_paper` and `download_pubmed` are traps, not tools.** `download_pubmed` raises `NotImplementedError` — PubMed serves no PDFs. Worse, `read_pubmed_paper` **returns successfully** with the string "PubMed papers cannot be read directly through this tool. Only metadata and abstracts are available…". That is an error message shaped exactly like content, and an agent that trusted it would write a paper note whose body is an apology from a library. Fourth member of the same family as the `abs:` over-restriction, the `search_paper_text` silent-empty, and Asta's 271-second connection error: the call succeeds, the payload is wrong, and only the prose prevents it being recorded as a finding.

- **Secrets live in a gitignored `.env`, never in plugin config, and the pipeline degrades without them.** Asta keys are personal — the two researchers should not share one — so `.env` (gitignored, mode 600) holds `ASTA_API_KEY` and `.env.example` is the committed placeholder documenting how to get one. `.mcp.json` references it as `${ASTA_API_KEY:-}`; the `:-` default matters, because Claude Code does **not** read `.env` automatically and an unset variable with no default is substituted **literally**, leaving a header reading `${ASTA_API_KEY}` and a server that fails confusingly rather than cleanly. Loading is manual and must be documented, not assumed: `set -a; source .env; set +a` before starting Claude Code.

  Degradation is enforced in the agent, not the pipeline. `second-brain-crossfield-searcher` runs a one-line `test -n "$ASTA_API_KEY"` before any search call and stops with an accurate message if it is absent — which also catches the *empty-string* case the `:-` default produces, and which would otherwise hang exactly as an absent key does. The pipeline dispatches the leg unconditionally and never checks for credentials itself: keeping that knowledge in one agent is what stops every caller needing to know about keys. A skipped cross-field pass is an additive enhancement missing, never a failed run, and the arXiv and PubMed legs are untouched by it.

- **Paper identity is now one shared spec.** `templates/paper-identity-spec.md` holds the DOI → source-id → normalized-title key ladder, the surname-slug filename rule, and the collision suffix; `second-brain-paper-downloader` had them inline and now cites the file instead, per the one-copy rule above. The ladder gained DOI at the top because every non-arXiv source supplies one, and a normalized-title match with differing DOIs is the preprint/published pair — the common arXiv+PubMed case, to merge rather than treat as a collision. Because the two legs run in parallel and cannot see each other's writes, cross-leg duplicates are resolved by the pipeline's merge step before the stage-4 checkpoint, not by the fetchers.

- **Each problem is its own Obsidian vault (2026-09-24).** The vault writer used to write links as `[[<problem-id>/papers/<id>]]`, correct only for a vault opened at `obsidian_vault/` so that several problems could share one. The researcher opened `obsidian_vault/<problem-id>/` instead — the natural choice, and where `.obsidian/` ended up — and every one of ~800 links in a 42-paper vault was dead. Links are now written from the problem folder (`[[papers/<id>|Title]]`, `[[topics/<kw>]]`, `[[repos/<owner>-<name>]]`), the pipeline passes `obsidian_vault/<id>/` as the vault path, and the writer refuses a path whose last segment is not the problem id. The cost is that one vault no longer spans problems, which nothing used. `scripts/check_vault.py vault` resolves every link the way Obsidian does after each run, so this class of bug is reported rather than discovered in the app.

- **A paper's id is its filename stem, fixed at download (2026-09-24).** The same paper used to carry three ids: the downloader coined one from the authors, `paper-summarizer` coined another from the title, and the code leg used the filename. Links written in one namespace pointed at notes named in another, and the vault writer repaired them by matching titles. Now every stage uses `YEAR_first_second`, which the filename rule already made unique and which any stage can compute from a path without reading anything. The vault writer no longer title-matches: an unknown id is reported. `scripts/check_vault.py records` checks id agreement, dead links and leaked tool-call markup before the vault is written. Note names are citekey-style; links carry the title as display text.

- **Every saved paper has an identity header, and full text comes from a script (2026-09-24).** arXiv files used to be bare copies of the MCP cache, so their DOI and arXiv id existed nowhere but the filename, and 16 of 42 summaries had no identifier — Semantic Scholar embedding coverage fell to 26/42. Every leg now writes the header in `templates/paper-identity-spec.md` from the source's metadata, and `paper-summarizer` copies identity fields from it before reading the body. Nine "full texts" in that run were note-shaped records or abstract stubs; the header's `full_text` field now says which is which, and the body is never summary-shaped.

  Full text: on the same run 16 of 20 clinical papers were abstract-only. In `paper-search-mcp`'s `download_with_fallback`, the PMC lookup reported open-access papers as closed, Europe PMC's PDF endpoint returned 403 (twice saving the HTML error page as a `.pdf` while reporting success), CORE failed on every DOI, and the Sci-Hub mirror did not resolve; only Semantic Scholar's hosted PDFs worked. `scripts/fetch_fulltext.py` replaces the open-access part with APIs: Europe PMC full-text XML (JATS converted directly, so no PDF and no garbled digits — one paper's Docling output rendered `0.90` as `Ͷ.ͿͶ`), NCBI BioC for NIH author manuscripts (Europe PMC's XML endpoint returns 500 for those), the arXiv PDF, Semantic Scholar's open-access PDF, and Unpaywall. It fills missing DOIs/PMIDs/PMCIDs from Semantic Scholar first, since a record with no id cannot be looked up in PMC. Every PDF must start with `%PDF-`. Tried on four papers from that run that had ended up without text: all four came back full, through XML, BioC and the arXiv PDF. Sci-Hub stays the biomedical leg's last rung via `download_scihub`, validated by the same script. 17 arXiv papers were dropped because `arxiv-mcp-server` lacked its `[pdf]` extra; that error is now treated as permanent (no retry) and the paper goes to the arXiv-PDF route instead.

- **Token spend: measure turns × context, and move deterministic work to scripts (2026-09-24).** The 42-paper reRD run cost 20.8M weighted tokens (input + 1.25 × cache write + 0.1 × cache read + 5 × output, over every turn of every transcript: `scripts/token_report.py <session>.jsonl --tools`). The harness's per-agent `subagent_tokens` is the agent's final context size, not its cost: every turn re-reads the whole context, so cost is turns × context. The split: `obsidian-vault-writer` 25% (63 turns over up to 670k of context, for a job with no judgment in it), `topic-summarizer` 22% (213 of its 392 Reads were summaries), `paper-summarizer` 20% (mostly output), the main conversation 16% (~75 background-completion turns over a context inflated by header reads and raw greps), discovery 17%.

  What changed:
  - The vault writer became `scripts/build_vault.py`, a port of its rules. Against the reRD vault it gives the same sections in all 83 notes, the same link targets, 0 dead links out of 802 and byte-identical BibTeX. It reads arXiv metadata itself, falling back to OAI-PMH: the query API answered HTTP 406 to every uncached request that day.
  - `scripts/stage_prep.py` replaces the main conversation's file reads with compact reports: the merge (redundant copies move to `.merged/`), the fan-out plan, the keyword index and the topic digests.
  - Fan-outs go in foreground waves, each returning as one turn. Dispatch prompts are templates, and agents reply `OK`/`FAIL` plus a few anomaly lines.
  - `paper-summarizer` batches short papers 8 at a time and reads a long one up to its references, plus an appendix the main text defers a formulation to.
  - `topic-summarizer` reads one digest per topic instead of one summary per paper. The digest keeps each summary's whole body, so the saving is turns, not bytes. Its full-text pass is budgeted: none for ≤3 papers unless a formulation is missing, otherwise ≤3 central papers × ≤3 regions.

  The subagent cap is Claude Code's (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20). A call past it is refused with "Do not retry", not queued; reRD lost 9 of one message's 14 dispatches to it. A wave never holds more calls than the cap, and raising the cap saves wall-clock time, not tokens.

  Deliberately **not** done, because each could weaken what the pipeline finds or writes: cutting search breadth (recall was an open defect; see the next entry), parallelizing calls within a discovery leg, scripting the search (PubMed retrieval has since been scripted, for recall rather than tokens: see "Core coverage" below), a fresh context for stage 5, word caps on summaries, trimming agent definitions (the fixed floor per agent is only ~7k), changing model tiers. Also not done: inlining the profile into dispatch prompts. A dispatch prompt stays in the main conversation and is re-read on every later turn, so twenty inlined 5 KB profiles cost more than the twenty small Reads they save. Target: about half the weighted total on a comparable run.

- **Recall is checked, not assumed (2026-09-24).** The reRD run missed Zhou 2023 (PMID 37013114, a nomogram for recurrent RD) and Gan 2025 (PMID 40235812, AI-PVR). They are two of the four closest comparators to the researcher's own model, and the run found the other two (Catania 2024, Fung 2023). No stage noticed. The PubMed leg ran 21 queries built as bare word lists, and PubMed ANDs every bare word. 5 of the 21 returned 0 hits, among them `machine learning deep learning retinal detachment surgical outcome prediction model nomogram risk score`. Its retry kept `machine learning retinal detachment prediction` and dropped `nomogram` and `risk score`, so Zhou matched no query the leg kept. That retry had 54 hits, but the leg read only the top 30, and Gan was #46. (An earlier version of this entry said 9 of 21 returned 0 and that neither paper was in any result set; replaying the queries showed both were wrong.) The same concepts as three OR-groups joined by AND — (RD synonyms) AND (recurrence/outcome synonyms) AND (nomogram/ML/prediction synonyms) — return 41 hits with all four comparators among them, at #4, #19, #22 and #36 by relevance.

  Two fixes:
  - **The legs query better.** The biomedical leg builds each query from 2–3 concept blocks and one sub-ask. It rebuilds a zero-hit query instead of reporting thin literature. Both paper legs list the queries that still returned nothing.
  - **The pipeline checks independently at stage 4.** `scripts/recall_check.py probe` runs the profile's new `recall_probes` on PubMed and arXiv and lists every top hit missing from the vault. These are 1–3 precise queries for the direct-comparator category: drafted at intake, or by the pipeline for older profiles. The researcher picks hits by number, and `recall_check.py add` saves them as identity-header records and runs the full-text fetcher.

  The discovery legs never read `recall_probes`: a check they queried with would be testing itself. On a copy of the reRD vault the probe lists both missed papers and finds Catania and Fung by DOI. `add` saved both missed papers with full text from Europe PMC. The hits include off-target papers (35 of the 40 checked were missing, most of them not comparators), which is why the researcher chooses rather than the script adding everything. arXiv's query API refused every uncached request for most of that day (HTTP 406), so the check reports that source as not checked rather than as 0 missing.

  **Superseded the next day** by "Core coverage" below. The probe detected only one of the three ways core papers were lost, and its own ML-only query missed the four classical models. It now runs as the citation chaser's first round, and the checkpoint's numbered pick-list is gone. `recall_check.py` became `find_papers.py`.

- **Tags drift across summarizer batches; untagged mentions are counted (2026-09-24).** The synonym merge at stage 5 step 2b fixes two slugs for one subtopic, but not a paper that never got the tag. On reRD, `2019_smeden_moons`, titled "…Beyond events per variable criteria", was tagged `sample-size-determination` while three other papers carried `events-per-variable`, and four summaries discussed scleral buckling without the `scleral-buckling` tag.
  - `stage_prep.py keywords` now shows, per slug, how many untagged summaries name it in their text.
  - `digest` lists those summaries with one sentence each under "Mentioned but not tagged".
  - `topic-summarizer` takes into the note's `papers` only the ones that cover the topic.
  - `build_vault.py` links a paper to a topic from that list as well as from its keywords, so a summary is never re-tagged after the fact.

  Detection is phrase matching on the slug and its aliases (hyphen or space, a plural allowed), so a slug that never occurs as prose (`machine-learning-prediction`) finds nothing. That is the case for giving the topic an alias.

- **A summary's year is checked against its paper's (2026-09-24).** One reRD source file carried "August 24, 2026" in its body against a 2023 publication. The header rule already prevents the cause, since identity comes from API metadata and `paper-summarizer` never overwrites it from the body. `check_vault.py records` now also warns `year_mismatch` when a summary's `year` differs from the paper header's, or from the filename's year for a paper with no header. On the reRD vault it flagged `2025_ozkut_navard`, an arXiv paper submitted in August 2025 whose summary says 2026.

- **Core coverage: the core question is covered exhaustively, by citation chasing (2026-09-25).** The day after the recall check, a fuller audit of the reRD run found the gap was systematic. The reference set was 15 papers that a well-built query finds and that are squarely on the core question (prediction models for RRD, re-RD and PVR outcomes), plus 4 classical PVR prediction papers (Asaria 2001, Kon 2000, Rojas 2009 and 2015). The run had 5 of these 19. The two 2026 systematic reviews of AI for vitreoretinal surgery outcomes include 6 RD/PVR studies, and the run had 4. Replaying the PubMed leg's 21 queries located every missing paper:
  - **8 matched no query** (Jia, Gao, Venkatesh, Burton and the four classical papers). The only core query used `machine learning` as its method term, and its retry dropped `nomogram` and `risk score`, so no classical model was searched.
  - **3 ranked below the window** (Gan, Zhou, Xing). The leg read the top 30; Gan was #46 of 54. 8 of the 21 queries were cut off, for example at 30 of 54 or 20 of 5,103. The MCP search tool reports no total and cannot page, so the leg could not know.
  - **3 were retrieved and not selected** (the Bernardi review, Nisanova, Desideri). 20 slots were split evenly over 6 review questions.

  Nothing caught what the queries missed: the clinical core rested on a handful of PubMed queries, the arXiv leg found one RD paper, and the cross-field leg covers methodology only. Tested on that run, one hop of citation chasing (references plus citing papers) from the 10 core papers it found recovered 10 of the 14, including all four classical ones. A concept-block query recovered the other 4. PubMed's "similar articles" recovered 1 of 10. Semantic Scholar returns empty reference lists for many clinical publishers; OpenAlex had 35 references for Catania and 29 for Fung where Semantic Scholar had 0, with no key.

  Four changes:
  - **`core_questions` in the profile.** On a topic profile it names the review question(s) to cover completely; a problem profile's core is its direct comparators. Intake asks for it, and the pipeline sends an older topic profile back to intake for that one field. The discovery legs save every core paper that passes screening and cap only the background questions at 20.
  - **Whole hit sets.** `scripts/find_papers.py pubmed` replaces the biomedical leg's MCP search. It reports every query's count, fetches a query of up to 300 hits whole, and flags a larger one as too broad instead of cutting it. A background query may be read top-50, and says so; a core query is split instead. The leg saves through `find_papers.py add`, which writes the header from PubMed's metadata and runs the open-access fetcher.
  - **Query rules.** Truncation and plurals; classical and ML method terms together in every prediction-type query; a retry widens a query, never removes a term from an OR-group.
  - **The citation chaser** (`second-brain-citation-chaser`), after the legs and before the merge. It runs the probes whole, without a date window. It then chases citations one hop both ways through OpenAlex (`find_papers.py chase`) from the vault's core papers, then from each round's additions, until a round adds nothing. It screens titles first and reads abstracts only for the unsure ones. It stops at 4 rounds or at 40 additions in one round, since either means the core question is too broad, and it never re-lists a paper an earlier round showed.

  On a copy of the reRD vault, `pubmed` returned the old 54-hit query whole, with Gan, Nisanova, the Bernardi review and Rojas 2009 in the list. `chase` from 10 core seeds (9 s) listed 498 candidates, among them Asaria, Kon, Rojas 2015, Zhou, Gao, the Gan preprint and Desideri. Its second round, from 7 of those, listed 296 more, leaving out 97 already shown. A concept-block probe found Venkatesh and Jia.

  **The chaser, run live on a copy of the reRD vault** (profile given `core_questions: [3]`, no `recall_probes`), took 36 turns, 17 minutes and 1.20M weighted tokens, about 6% of the original run. It made 24 OpenAlex and 20 NCBI requests. It drafted probes and split the too-broad ones, then chased three rounds from 6 seeds: 516, 599 and 55 candidates. It stopped when round 3 added nothing, having added 32 papers. 10 of them came with full text, and the other 22 went to the needs-manual-download list.
  - **Recovered 11 of the 14 missed papers:** Jia, Gao, Venkatesh, Asaria, Rojas 2009 and 2015, Gan, Zhou, the Bernardi review, Nisanova, Desideri.
  - **Kon 2000 and Burton 1977 were listed and rejected** as risk-factor studies, following the agent definition's own example. Its screening bar now counts a multivariable analysis of predictors as classical prediction work. Burton's 1978 predictive-model paper was never listed.
  - **Xing was never listed.** The drafted probes had no PVR branch, and OpenAlex holds no reference list for it. Drafting now asks for one probe per outcome the core question takes in.
  - **One screening slip:** the agent passed a number from one list with another list's name and saved an unrelated paper, then deleted it. Candidate numbers now carry on across a vault's lists, and `add` refuses a number not in the named list.

  These three fixes are not yet tested in a live run.

  OpenAlex's keyless budget is $0.10 a day: about 1,000 filter requests, or 100 title searches. Each hop is a few batched filter requests of up to 100 ids each, and only a seed with no DOI, PMID or arXiv id costs a title search. `OPENALEX_API_KEY` raises the budget tenfold.

- **Topic deep-dive: a literature search for one topic note of an existing vault (2026-09-25).** A vault's topic notes come from the papers its one review found, and the picker's "deepen" rewrites a note from those papers only. A researcher reading a vault wants to say "go deeper into *this* topic" and get new literature on it: the note deepened when it exists, created when it does not, and linked into the vault either way. `second-brain-topic-deep-dive` is the entry skill. It resolves the vault and the note with `stage_prep.py topic`, then hands over: the Q&A to a deep-dive branch of `research-problem-intake` (`deep-dive.md`, a drafted profile confirmed in 1–3 turns), and stages 3–5 to a deep-dive branch of `second-brain-pipeline` (`deep-dive.md`). No orchestration is duplicated, and the branches live in their own files so a normal run does not carry them on every turn. Design choices:
  - **The deep-dive profile is a topic profile.** Scope, purpose, 1–4 questions and a core question, about the topic alone, plus `deep_dive_of`, `vault_profile`, `topic_note` and `topic_aliases`. Every discovery leg and the citation chaser run on it unchanged. Its `paper_vault_path` is the vault's, so new papers land in the vault's paper vault and each leg's dedup skips what is already there. It lives in `<root>/deep_dives/<vault-id>/`, never in the paper vault, whose top-level `.md` files every script reads as paper records.
  - **Everything that writes vault content gets the vault profile.** `paper-summarizer` tags each summary with `Q1…` against the profile's `review_questions`, and `stage_prep.py keywords` counts those tags across all summaries; summarized against the deep-dive's questions, the new papers would miscount in every later index and carry the wrong `related_problem`. `build_vault.py` refuses any profile whose id is not the vault's anyway. Only `topic-summarizer` sees both: the vault profile for relevance, the deep-dive profile for scope, questions and depth.
  - **Only the slug is added to the vault profile**, with consent, to its `keywords_of_interest`, so `paper-summarizer` files new papers under it; exact reuse of that slug is the only thing that matches a paper to a topic. Never an alias: an alias listed there would get a note of its own on the next normal run.
  - **Seeds are written `"<exact title> — <doi>"`.** `find_papers.py` takes a DOI from anywhere in a seed, but otherwise reads the whole string as one id or one exact title, so a vault id or a trailing YAML comment makes a seed unfindable. The topic report prints a ready seed line per paper.
  - **A snapshot tells the deep-dive's papers from the vault's.** `topic --snapshot <id>` records the vault's records and summaries in `<paper vault>/.deep-dive/<id>.json`, and keeps an existing one, so a resumed run does not move the baseline. `topic --since` reports against it at stage 4 and after the summaries (new records, full text, which carry or name the slug, which other notes gained papers), and `digest --since` adds the papers the search saved that carry neither the slug nor an alias and do not name it: the summarizer tagged them with the vault's vocabulary, but the search found them for this topic.
  - **The note is deeper, and stays so.** `topic-summarizer` gets up to 6 central papers × 4 regions of full text, with no "3 papers or fewer" exemption, and writes 600–1,000 words of prose (up to ~1,400 when deepening) plus up to ~600–800 of technical detail; its relevance section answers each deep-dive question in turn. The note carries `deep_dive: <id>`, and a later normal re-run that deepens it may not make it shorter: without that marker, the normal deepen caps of ~600/400 words would cut it back to a normal note's size.
  - **`## Related topics`, owned by vault-build, on every topic note:** the other topic notes sharing at least 2 papers, at most 5, taken greedily by shared count while both notes have a free slot, so every link has its way back. A topic's papers are the ones its note lists plus the ones tagged with its slug or an alias, the same two ways a paper note links to a topic. Counting listed papers alone was tried first and failed on the live run: the deep-dive's 58 new papers are listed only by the rebuilt note, since other notes are not rewritten, so the note related to one topic only. It links a deep-dive's note to the existing topics and them back to it, and applies to normal runs too, through an owned section only.
  - **No code leg.** A deep-dive is about the literature on one topic.
  - **Old-id vaults are refused.** A vault whose summary ids are not filename stems, or whose note lists ids that are not papers (the reRD vault, built before ids were fixed), would get links that do not resolve. The topic report warns, and the skill stops.
  - **One deep-dive per vault at a time**, since candidate lists, digests and linker state are shared.

  **Live test, on a copy of the reRD vault** (migrated to filename-stem ids by a throwaway script first; the topic report refused the unmigrated copy with its old-id warning). The plugin's agents were run as general-purpose subagents told to follow their definition files, with the definitions' models, and the researcher's two turns (confirming the draft, the stage-4 go-ahead) were stood in for.
  - **Run A, the existing note `survival-analysis` (4 papers):** the draft took one turn, and the vault profile changed by one line. Discovery saved 75 new records (arXiv 18, PubMed 38, chaser 19 over 4 rounds, stopped at the cap), 37 full text; the cross-field leg skipped for want of a key and the code leg did not run. The summarizers got the vault profile: every new summary carries its `related_problem` and cites only Q1–Q6. 45 of the 75 carry the slug, since it had been added to `keywords_of_interest`; the other 30 went to the digest's found-untagged list, and the summarizer took 13. The digest ran to 2,347 lines, past one `Read`. The note grew from 4 to 62 papers with `deep_dive` set, one relevance paragraph per question (1 partly, 2 partly, 3 answered, 4 partly), inline links only to existing topics, and the researcher's `## My notes` intact; no other topic's content changed. It ran about 15% over the soft caps (1,633 prose words against ~1,400, 914 technical against ~800). 41 of the new papers got links to papers the vault already had; records and vault checks clean (two summaries had leaked trailing markup, which `--fix` stripped); 0 dead links. Agent cost 9.76M weighted tokens: summarizers 5.24M, topic-summarizer 1.56M, chaser 1.43M, the legs 1.53M. The original full 42-paper run cost 20.8M.
  - **Fixed from the run:** `## Related topics` counted listed papers only, so the note related to one topic; it now counts tagged papers too, and the note relates to five, each linking back. The topic report's nearby slugs let every keyword of a one-paper topic crowd out the one real alias (`ultra-wide-field-imaging` for `ultra-widefield-imaging`); they now come in three kinds, with spelling variants and joined words (`wide-field` = `widefield`) first. The summarizer's report flagged replacing the record of the note it was deepening from the Obsidian copy as an anomaly; that is the normal case, and the definition now says so. A `--since` list of 75 unsummarized ids now prints only when it is short.
  - **Run B, a new topic (`ultra-widefield-imaging`), was stopped after discovery** to save tokens: 43 new PubMed records, none from arXiv. Creating a note with no existing one in deep-dive mode is therefore tested only offline, in the topic report's fixtures, not with `topic-summarizer`.

## Prior art reviewed

Surveyed 2026-08-31. Conclusion: **the pipeline architecture is the part worth keeping.** The CLAIM-checklist intake, the two-pass close-field/generalized-methodology search, the stage-4 checkpoint and the per-problem keyword taxonomy are not replicated by anything found. What *is* done better elsewhere is source breadth, full-text extraction, identity/dedup, and embedding similarity — those are the adoption targets.

**Adopt (planned):**

- **paper-search-mcp** (MIT, ~2.5k★) — 30+ sources (arXiv, PubMed, PMC, Europe PMC, bioRxiv/medRxiv, Semantic Scholar, Crossref, OpenAlex, CORE, Unpaywall), unified search with cross-source dedup, and an OA-first download fallback chain. Ships as MCP server, `paper-search` CLI, *and* a Claude Code Skill.
- ~~**BioMCP** for the PubMed leg~~ — **dropped on closer inspection; see "Reviewed and rejected" below.** `paper-search-mcp` covers the same literature sources, and BioMCP's differentiated surface is precision-oncology machinery this project does not touch.
- **Ai2 Asta Scientific Corpus Tool** — hosted MCP (`https://asta-tools.allen.ai/mcp/v1`, `x-api-key`) over Semantic Scholar's ~200M-paper index. The important tool is **snippet search over paper bodies**: cross-field transfer hits are usually invisible in an abstract and visible in a methods section, so this is the best available fit for the generalized-methodology pass — the pass the current arXiv-abstract-only design serves worst. Also supplies citation counts, i.e. the ranking signal the dedup/ranking open question needs.
- **Docling** (MIT, IBM) — the missing non-arXiv full-text path; `arxiv-mcp-server`'s cached extraction only exists for arXiv, so PubMed/PMC/OA PDFs currently have nowhere to go. GROBID is faster on scholarly PDFs and emits real section structure as TEI XML, but renders formulas and tables as images; Docling wins here because the output feeds a Markdown vault.
- **SPECTER2** (Ai2) — answers the open embedding-model question: scientific-document embeddings over 23 fields including Medicine, with an adapter trained for exactly the "similar papers" recommendation task. Generic sentence embeddings are the wrong tool. Zero-infrastructure alternative: Semantic Scholar's Recommendations API via Asta (no local model, no index).

**Adopt if going further:**

- **PaperQA2** (Apache 2.0, ~9.1k★, FutureHouse) — agentic RAG answering with in-text citations over a folder of papers. The paper vault is already that shape, so `pqa ask` over `paper_vault/<id>/` is nearly free and adds grounded cross-paper Q&A and contradiction detection, which this plugin has no equivalent of. CLI/Python only, no MCP. Successor PaperQA3 is commercial — stay on 2.
- **Obsidian Local REST API v4** — now ships a *built-in* MCP server (`vault_read`, `vault_patch`, `search_query`), no bridge needed. `vault_patch` edits one heading without touching the rest of the file, which is precisely the deferred merge-on-rerun-preserving-manual-edits requirement. Decided: adopt as an **optional** path in `obsidian-vault-writer`, falling back to plain file writes — the "vault-build never depends on Obsidian" constraint above stays intact because the fallback *is* the current behavior.
- **Obsidian Smart Connections** + `smart-connections-mcp` — local on-device vault embeddings, zero setup, no API key; the MCP bridge just reads the `.smart-env/` files it already computed. Weaker than SPECTER2 on scientific text, but gives ambient cross-problem "related notes" with no index for this plugin to maintain.

**Reviewed and rejected:**

- **academic-research-skills** — large multi-agent academic suite, but licensed **CC-BY-NC 4.0**, which rules out adoption regardless of quality. Worth reading for its integrity/verification gate design; do not vendor.
- **claude-knowledge-vault** (MIT, ~33★) — architecturally the closest thing that exists (ingest → `.vault/wiki/` with wikilinks, Obsidian-browsable, arxiv-mcp + paper-search-mcp + zotero-mcp backends), but has no problem profile, no checkpoint, and no keyword taxonomy. Confirms this layering rather than replacing it.
- **obsidian-vault-agent** (MIT, ~37★) — one idea worth stealing outright: its `/paper-discover` ranks hits by relevance **to the existing vault**, not to the query alone. `/vault-graph` (PageRank, bridge detection, orphan identification) is a cheap health check for a keyword-linked vault.
- **Zotero MCP** — deferred; Zotero is not currently in either researcher's workflow. Noted because adopting it would close the duplicate-identity, BibTeX and PDF-storage open questions at once. Revisit if that changes.
- **Standalone Semantic Scholar MCP servers** — several unofficial ones; Asta supersedes them (same corpus, adds full-text snippet search, Ai2-maintained).

## Open questions for the team to brainstorm

Do a real `/plugin install` + invocation before treating this as fully closed.
- Note schema: exact YAML frontmatter fields, naming convention for files/IDs. **Now urgent rather than cosmetic:** `paper-summarizer` derives a paper `id` as a title slug plus *today's* date, and the `related_notes` edges written by `scripts/link_papers.py` point at those ids. So re-summarizing a paper on a different day changes its id and breaks every inbound edge, and two similarly-titled papers summarized the same day can collide outright.
